# Verification architecture for the mod monorepo

Status: researched design, with bounded local engine/Docker probes on 17 October 2026 and isolated tool/blueprint/RCON follow-up spikes on 18 October 2026. This extends [the monorepo migration plan](MONOREPO_MIGRATION_PLAN.md); it does not implement the proposed toolkit or authorize publication, normal-profile installation, account changes, or interference with existing game instances.

Use [section 9](#9-delivery-and-acceptance) as the implementation checklist and sections 1–8/10–13 as its detailed requirements and research evidence. An unchecked required capability is missing or blocked, not implicitly optional. Completed research is tracked separately in the migration plan; the existing 1.1.7 prototype evidence below does not complete the shared toolkit.

## 1. Recommended execution lanes

Make unattended verification a first-class toolkit capability, not a collection of instructions for an agent to click through. Use the same Bun + Effect orchestration, Effect CLI entrypoint, Effect Schema contracts, project resolver, and evidence format for each execution backend.

| Lane | Recommended environment | What it establishes | What it cannot establish |
| --- | --- | --- | --- |
| Fast local checks | Host Bun and pinned language/tooling dependencies | Schemas, types, pure-model invariants, package structure, tooling behavior | Factorio engine behavior |
| Routine engine verification | Pinned official Linux headless Factorio in Docker | Prototype loading, runtime scenarios, real saves/upgrades, packaged behavior, failure diagnostics | Graphics, hit testing, native macOS behavior |
| Native/rendered verification | Pinned official non-Steam full Factorio build in an isolated profile | Actual native rendering, GUI structure, visual regressions, platform-specific behavior | Other renderers/platforms without separate runs |
| Presentation capture | Separate full-client instance, always Extreme | Thumbnails, gallery images, deterministic GIF/video frames | Test-speed measurements representative of ordinary test profiles |
| Compatibility and soak | Explicit selected engine/mod/architecture matrix | Named integration, persistence, load and multiplayer risks | Universal compatibility with all mods or platforms |

Docker is the recommended portable headless backend, not a requirement for every tiny edit and not a second implementation of the test system. A native executable can be an explicitly selected backend using the same contracts. Never silently switch backend, engine version, graphics settings, or test scope after a failure.

## 2. Alternatives to the Steam custom-argument dialog

The supplied screenshot establishes that the current graphical launch can reach Steam's **Launch Game with custom arguments** confirmation. Treat this as a blocking interactive dependency, not something to automate away. A launcher process exiting successfully is not evidence that Factorio initialized or ran the intended executable.

Valve documents that `SteamAPI_RestartAppIfNecessary` can relaunch through `steam://run/<AppID>` and select the Steam-library executable rather than the original executable. This explains why merely finding an executable path does not guarantee direct process ownership. It is a relevant mechanism, not a traced diagnosis of the supplied invocation. Factorio staff explicitly recommend the website's DRM-free binary for mod development. [Steamworks](https://partner.steamgames.com/doc/sdk/api#SteamAPI_RestartAppIfNecessary), [Factorio staff guidance](https://forums.factorio.com/viewtopic.php?t=109485).

| Option | Decision and tradeoff |
| --- | --- |
| Official standalone macOS full build | Preferred local graphical route. Launch its actual executable with explicit config/mod/save paths. Pin the distribution and version independently of the player's Steam installation. Requires legitimate full-game/expansion access and a usable graphics session. |
| Official Linux headless build in Docker | Preferred Steam-independent bulk engine route. Public download, no Steam client, no desktop, deterministic provisioning. The official current headless distribution includes Space Age content. Does not contain a usable screenshot renderer. |
| Installed Steam executable in headless mode | Useful explicitly selected local route: the probes below succeeded without Steam environment overrides or interaction. Do not generalize that result to graphical startup or to every Steam/engine version. |
| Full standalone Linux client on a graphics-capable worker | Viable future unattended rendering lane with pinned renderer/driver/display. Requires the full distribution, graphics libraries, and a proven render context; a server-only image is insufficient. |
| Full Linux client with a virtual display/software renderer | Research candidate for automated GUI/render assertions, not an established solution here. A virtual display does not supply a GPU. Validate actual output, Extreme support, cost and fidelity before adopting it; do not substitute its timings for native GPU performance. |
| Persistent full-client development session | May reduce interactive iteration cost for selected tests, but retains state and does not exercise cold startup, data-stage changes, package closure, or real upgrade loading. Not release evidence or a replacement for isolated runs. |
| Steam launch options, `steam://`/`open` wrappers, developer App-ID hints | Not the canonical unattended runner. Steam remains a dependency; launch arguments, relaunch behavior and process ownership remain problematic. Existing runners set `SteamAppId`/`SteamGameId`, and Valve documents developer App-ID hints, but neither is proof of a reliable graphical lane. Do not click confirmations, disable safeguards, edit the player's Steam installation, or add an automatic workaround chain. |

The local `~/Applications/Factorio.app` candidate is only a shell wrapper for `open steam://run/427520`, not a standalone installation. It must not satisfy a standalone-engine prerequisite.

Provisioning is separate from running tests. Factorio's [FAQ](https://factorio.com/support/faq) describes linking an existing Steam purchase to a Factorio.com account for website access; linking/login remains a human-authorized account action, never a hidden test-run step. A properly provisioned local engine must run tests without repeatedly logging in or downloading mods. Do not use the demo as a full mod-testing engine. Record exact builds from the [archive](https://factorio.com/download/archive/2.1.21), not floating `stable`/`experimental` URLs in verification receipts.

## 3. Docker contract

Use ordinary short-lived containers, not a permanent game server or a new orchestration platform. The host toolkit owns their lifecycle; there is no need to mount the Docker socket inside a container.

- Pin the official Factorio archive URL and SHA-256, the OCI image digest, target platform, and required runtime libraries. Verify downloads before extraction. A published checksum is an integrity check, not a claim of a separate signature chain.
- Select the platform explicitly. This machine's Docker daemon reports Linux `aarch64`; official 2.1.20/2.1.21 ARM64 headless archives are available. Older declared 2.0 targets need their own supported artifact/platform mapping; do not silently move them to 2.1 to obtain ARM64 support. Record any x86 emulation and use native x86 workers when its cost matters.
- Resolve host paths to a typed container mount plan. Expose only immutable engine/dependency/input artifacts and one owned writable run directory. Do not mount the whole home directory, normal Factorio profile, credentials, or unrelated worktrees. Prefer a source snapshot or exact package over a live source bind during sealed verification.
- Run non-root, drop capabilities, use a read-only root filesystem, bounded writable temporary storage, and explicit CPU/memory/PID limits. Preserve caller-readable output ownership. No privileged containers or host networking.
- Separate online provisioning from offline execution. Ordinary single-process engine checks need `--network none` and no published ports. Multiplayer/RCON checks use an explicitly isolated network or loopback-only binding, with no public listing, LAN advertising, or exposed administrative port.
- Keep engine/input mounts read-only; Factorio's config, `write-data`, mod list/settings, saves, logs and `script-output` belong to the run. Treat engine-rewritten config/mod lists as observations, not as permission to change source configuration.
- Track container IDs and ownership labels, not just a generic name. On timeout/cancellation, stop only the owned container; killing the `docker run` client alone is insufficient. Gather container state, exit code, `OOMKilled`, logs and artifacts before removal. Exit 137 alone does not prove an OOM.
- Do not use `--rm` before collecting state needed to diagnose a failure. Remove owned containers once evidence is durable. Bound image/cache retention without pruning another task's containers or volumes.
- Measure bind-mount I/O versus staged container-local data only if it becomes material. Preserve artifact export on failure; do not trade durable diagnostics for a fast happy path.

The local probe demonstrated that Debian Bookworm's libc was insufficient: the 2.1.21 ARM64 binary requested `GLIBC_2.38`. Digest-pinned Debian Trixie ran successfully without installing extra packages. The resolver must test the actual executable/runtime pairing, not assume historical Linux minimums apply to a new architecture.

Docker Desktop's documented `--gpus` passthrough to Linux containers is a Windows/WSL2 facility; it is not a promise of Metal rendering inside this Mac's containers. Keep native Mac graphics separate. See [Docker platform/emulation guidance](https://docs.docker.com/build/building/multi-platform/) and [GPU scope](https://docs.docker.com/desktop/features/gpu/).

## 4. One launch, supervision, and evidence boundary

Define one schema-backed run request and one versioned run receipt. Both native and Docker execution consume the same validated plan; backend-specific fields remain explicit discriminated variants. Existing Python helpers and external tools use validated request/result boundaries, not parallel handwritten parsers.

The runner must perform these transitions:

1. **Resolve:** exact mod ID, source/ZIP identity, engine distribution/build/architecture, dependencies, profile, capability requirements, suite/scene selection, locale, seed and resource limits. Validate before side effects; help/invalid arguments do not provision or start games.
2. **Prepare:** allocate a unique worktree/mod/profile/run directory, stage exact inputs, write isolated config and establish ownership. Include every bundled mod such as `recycler` in the intended enable/disable set. Record requested state before Factorio rewrites any file.
3. **Launch:** invoke the actual executable or explicitly selected container using an argv array, not a shell string or desktop launcher. Persist the redacted command, start time, input hashes, PID/container identity and expected evidence before waiting for completion.
4. **Observe:** stream stdout and stderr durably as they arrive; retain stream identity and receive timestamps, without pretending two pipes have a perfect total order. Read the run-owned `factorio-current.log`, structured framework/scenario results, and declared artifacts. Keep bounded diagnostic excerpts in memory, not the entire lifetime log.
5. **Classify:** distinguish prerequisite failure, launch failure, mod/data error, assertion failure, runtime Lua error, suspected native crash, timeout, cancellation, invalid/incomplete evidence and success. Preserve raw exit/signal/container facts alongside the classification. A Lua error is not a native engine crash.
6. **Finalize:** require expected assertions and artifacts, verify identity/freshness/completeness, capture the effective mod/config/renderer state, then write the final validated receipt atomically. Preserve diagnostics even if cleanup fails; report cleanup failure separately rather than masking the original fault.
7. **Release:** reap only owned processes/containers and release locks. Never `killall factorio`, close an unrelated game, clear arbitrary profiles, or silently rerun a failed check until it passes.

Use Effect scopes for child/container/lock lifetime and typed errors carrying phase, target, run ID and evidence locations. The same schemas should drive CLI output and machine-readable results. Schema decoding is necessary but insufficient: check semantic identity, hashes, suite completeness, and actual runtime observations.

### Live logs for running tests and tuning sessions

Live observation is required for headless tests, native scenes, package smoke and long-lived tuners, on both native and Docker backends. Readers must not wait for process exit or the final receipt. Publish a schema-validated active-run record before launch and update its observed state; discovery identifies the exact run ID, mod, session kind, suite/scene, backend, start time and log locations. A missing supervisor or disconnected collector is an explicit unknown/interrupted state, not evidence that a test passed or the engine stopped.

Use the same run service for bounded historical reads and live following. Preserve stdout, stderr, engine-file output and structured test/tuner events with source identity, capture timestamp, engine tick when available, and a run-bound resumable cursor. Collector sequence is ingestion order, not a claim of total causal order between engine streams. Keep raw text intact; do not invent severity for unclassified lines or silently merge duplicate messages from different sources.

Readers can attach from another terminal or agent, inspect recent output, request only records after their cursor, filter by source/event kind, and follow new records. Offer human-readable output and Effect Schema-validated JSONL with cursor/checkpoint information. Filters operate on views, not on retained raw evidence. Bound snapshots and reader buffers; handle partial UTF-8/lines, multiline stacks, file rotation/truncation and final stream draining. Report retention/cursor gaps explicitly rather than silently restarting at an unrelated offset.

The collector persists output incrementally and independently of subscribers. A slow, absent or disconnected reader must not block the engine or cause silent evidence loss; bound buffering and make recording failures visible. Multiple read-only subscribers must coexist. Cancelling `--follow` detaches only that subscriber—it must never cancel the test, close the tuner, signal Factorio or stop its container. Follow ends after the terminal run state and remaining records are delivered. Idle tuning sessions remain readable; silence is not completion.

Tests expose phase/case start, completion and failure as they occur, without asserting final success early. Tuners emit parameter-change acknowledgements with revision and effective values, plus reset, scene, capture, export and error events. Do not log an unchanged parameter set every simulation tick. In-game chat/`player.print` alone is not the log transport: emit explicit companion events to the captured output or run-owned file protocol so agents can read tuning activity without opening the console.

Capture and observer lifetime must not depend on a particular reader terminal. Use owned run records and durable files with the existing supervisor; no centralized telemetry service is required. Read-only discovery/follow must never attach to arbitrary personal Factorio instances, enable debug settings, or request remote control. Apply the same credential/redaction boundaries as other diagnostics.

Acceptance includes observing a new event **before the producer exits**, two simultaneous subscribers, cursor reconnect without omissions or duplicate delivery at the API boundary, and cancelling a reader while the owned session continues. Exercise both test and tuner event streams, native and Docker sources, partial writes/rotation, quiet and noisy periods, recording failure, producer crash and final drain. Test these contracts with disposable producers plus real engine/session smoke; replaying a completed log is not live-stream proof.

### Deadlines and honest completion

Use separate provisioning, startup, execution, screenshot-flush and shutdown deadlines informed by observed workloads. Add an overall wall-clock cap: a process printing endless logs must not reset the only watchdog indefinitely. Quiet computation is not necessarily a hang, and continuous output is not necessarily progress. Preserve tick/progress observations where the harness has them; do not fabricate progress from log volume.

An expected diagnostic fixture may terminate nonzero and still pass its *failure-capture test*. An ordinary gameplay suite cannot. For a native harness that intentionally terminates the client after completion, record that termination separately and require all scene/assertion results plus fully flushed captures first; do not rewrite the process exit as zero.

A success marker, zero exit, file existence, nonzero passed count, or lack of an exception is never sufficient by itself. Reject stale/foreign receipts, missing expected cases, duplicate case IDs, forbidden focused tests, unexpected skips/cancellations, truncated output, and success followed by a later runtime failure. Establish the expected selected case set independently of what happened to finish; keep legitimate filtering explicit.

### Crash and failure readback without desktop automation

Factorio writes `factorio-current.log` and rotates the previous log in its user data directory. An explicit isolated `write-data` path makes this discoverable without opening Finder, Steam, or the game. Stream/copy evidence before another launch can rotate it. Retain full multiline Lua stack traces, the first relevant failure, startup/build/mod identity, and a bounded final diagnostic window. [Log format and privacy](https://wiki.factorio.com/Log_file).

Capture available run-owned native dumps and desync archives too. If a genuine native crash lacks sufficient engine diagnostics, a platform-specific collector may inspect only new crash reports matched to this exact executable/PID/time; do not sweep unrelated system reports or claim a dump must exist. Missing crash artifacts are a reported fact. Do not invent a universal `--disable-crash-dialog` switch: the inspected 2.1.21 help did not advertise one. Headless Lua failures were verified; native crash/modal behavior was not.

Logs, save fixtures and dumps may contain usernames, paths, server details or credentials. Retain local raw evidence with bounded retention; produce a redacted diagnostic bundle for deliberate sharing. Collection is not authorization to upload logs or saves.

### Agent-facing commands

Extend the existing Effect CLI rather than teaching agents per-backend shell recipes. Proposed, not implemented:

```sh
mise run doctor -- reversed-underground-belt-detector
mise run verify -- reversed-underground-belt-detector
mise run test-ui -- reversed-underground-belt-detector en
mise run runs -- --active
mise run runs -- <run-id>
mise run runs -- <run-id> --logs --follow
mise run runs -- <run-id> --logs --after <cursor> --limit 200 --format jsonl
```

`doctor` reports resolved engine/distribution/architecture, Docker/runtime compatibility where selected, dependency availability, required capabilities and missing prerequisites. It does not install, log in, change accounts or launch a graphical game. `runs --active` discovers owned sessions; an exact run lookup reports current/final state, diagnostic details, artifact paths and reproduction inputs. `--logs` reads output while the session is running or after completion; `--follow` subscribes without taking control, and cursor-based bounded reads suit agents that must not block indefinitely. Reproduction must be an explicit new run with its own ID, not a hidden retry. Existing `verify`, `test-ui`, tuning and release commands consume this boundary; no special unvalidated escape hatch for one mod.

## 5. Verification methods and proof boundaries

### Static and model checks

Retain syntax, formatting, Factorio-version-aware Lua types, locale-key checks and existing model/tool tests. Generate APIs for the target engine and keep per-mod storage types separate. Add behavior-focused validation of config precedence, path containment, dependency resolution, package membership and wrong-target evidence. Do not pin source text or implementation wording as a substitute for behavior.

For pure planner logic, property/state-machine testing can cover sequences such as edit/apply/discard/reopen, stale revisions, source removal and cross-player drafts. Use deterministic seeds and a small independent invariant/reference model. Preserve a failing seed and minimized action trace; a reimplementation of the production algorithm is not an independent oracle.

### Prototype and dependency checks

Use `--dump-data` to inspect the fully resolved prototype result, with exact startup settings and mod set. Decode only the relevant external fields, then assert intended recipe/technology/entity relationships and absence of unintended owned changes. Prefer focused semantic projections to massive golden copies of all `data.raw`.

Use `--check-unused-prototype-data` as targeted diagnostic evidence, distinguishing owned regressions from inherited dependency warnings. `--dump-prototype-locale` and `--dump-icon-sprites` can supplement locale/icon checks on capable builds; validate which modes require graphics before scheduling them. A headless prototype pass does not establish that graphical assets load or look correct. Prototype locale dumps also do not cover every runtime GUI locale key.

Always retain a standalone dependency-closure check. A broad modpack or combined harness can accidentally supply an undeclared dependency. Assert actual active names/versions against the intended allowlist, including bundled expansion modules, rather than trusting only the requested mod list.

### Real-engine runtime and event paths

Use pinned FactorioTest for existing suites and deterministic external scenarios for black-box package checks. Keep the single-primary-mod rule in the migration plan. Assert public behavior over engine ticks: entity state, alerts, tags, ownership, inventory/recipe changes, and cleanup—not elapsed ticks alone.

For the detector, cover valid and reversed pairs in every orientation; isolated/unpaired ends; same-force versus other-force visibility; rotation, destruction, replacement, scripted/robot construction where supported; setting changes; surface removal; existing-map installation; and correction after an active warning. Verify two mouth indicators and only the input end's span across each qualifying pair, without duplication after repeated events, while preserving unrelated alerts/rendering. Pulse/opacity and hierarchy additionally need rendered evidence.

Carry forward the 1.1.7 regression coverage: all available underground tiers including Space Age turbo, maximum reach/adjacency and mixed-tier/force cases, clone/revive/death, surface cleanup, pair-specific hover, pulsing/steady/off audiences, alert ownership, repeated lifecycle events, queue churn and overload. Assert no more than 64 scheduled background mouth entries per tick, fair progress after population shrink, next-tick dirty-neighborhood priority, preservation of work beyond 1,920 pairs, and explicit silent-change validation/native-alert latency. Keep partial-queue recovery and cleanup across actual `game.reload_mods()` as fast regressions; add disk-save proof separately. Do not impose the 64-entry background cap on unrelated event, survey, pulse or native-alert paths that are not covered by that contract.

Metamorphic cases can translate or rotate the entire fixture while preserving equivalent warnings, or vary creation order and check the final stable state. The planner's corresponding invariants include private drafts, no physical-character movement during remote navigation, stale-save rejection and preservation of recipe identity when map text is hidden. Combine local unit/model assertions with engine observations rather than testing the same mock at multiple layers.

Useful planner/lookup properties include semantic connection-set preservation under recipe duplication/permutation, anchor idempotence, and stable closest-source selection under enumeration changes or added ineligible candidates. Preserve deliberate order-sensitive product behavior: the first recipe's icon/default title need not remain unchanged under permutation. Assert tie-breaking and chart/force visibility, not merely that some candidate was returned.

Label input evidence honestly. Calling a handler directly tests handler behavior; `script.raise_event` creates a synthetic event; engine operations that raise documented events test those paths. None by itself proves a real player mouse click, keyboard binding, robot action, or hit target. Use actual engine actions/replay or a narrowly scoped native input check where that is the claim. Do not add production remote interfaces just to make tests convenient.

### Real save, restart, and upgrade checks

Create deterministic small saves with the **old shipped artifact**, not fabricated current-schema tables. Record engine, source ZIP hash, mod/settings set, scenario seed and intended preconditions. Preserve the clean-main baseline fixture required for detector extraction.

Run a multi-process sequence: establish state, write an actual save, terminate cleanly, load that save in a new isolated process with the intended artifact set, assert behavior, save again and reload again. Verify migration-once behavior and resumed event registration; cover new install into an existing map, old-to-new upgrade, removal/re-addition where supported, and config changes. Do not assert unsupported downgrade compatibility.

`game.reload_mods()` is useful fast coverage of mod reload behavior but is not proof of serialized save bytes, a process restart or artifact migration, and does nothing in multiplayer. `game.reload_script()` reloads the scenario script, not the whole game's mod lifecycle. A private headless server can perform explicit saves via the engine/server console or a bounded RCON harness; scope administrative access to that owned test instance. Asynchronous save requests must be observed as completed before loading their output.

For the split, load the old LLL fixture with upgraded LLL alone and with the new detector. Confirm old warnings retire narrowly, plans/tags survive, unrelated alerts/render objects survive, and only the new detector resumes detection. Observe packaged behavior externally without enabling FactorioTest or adding a test-only production interface.

### Exact-package and release verification

Validate archive identity and members, dependency closure, locales, migrations, licenses and assets. Compare repeated builds for deterministic bytes where promised. Exercise the sealed ZIP in a fresh profile with no source symlink or sibling checkout; a source test cannot certify the ZIP.

Record the actual builder/compression runtime as part of reproducibility inputs, including Python/zlib where the existing packager uses them. Fixed ZIP timestamps/member order alone do not establish byte identity across different compression runtimes. Existing release unit tests use placeholder ZIP bytes and header-only PNG fixtures; retain them for release-state contracts, but do not count them as archive or image-decoding proof.

Run enough real behavior to cross detection and cleanup boundaries. The existing ten-tick loader does not prove a full background-validation/native-alert cycle; overload can extend that cycle. Observe the actual outcome within fixture-specific declared bounds. Bind each result to the exact ZIP hash and all relevant companions; no rebuild after proof. Test wrong-target, stale, tampered, missing-input and same-version-cross-mod evidence rejection.

Exercise local release preparation and failure handling without publishing. Use controlled transport fixtures for network error/unknown-outcome contracts, not real Portal mutation as a test. Actual publication remains separately authorized and requires the existing mutation/readback safeguards.

### Native UI and visual evidence without routine computer use

A full client can load an isolated scene directly and let Lua create the scene, run GUI assertions and call `game.take_screenshot`. That removes routine desktop navigation from capture, while still using the real renderer. The API explicitly does nothing when headless. Use `show_gui`, an explicit camera/zoom/resolution and deterministic surface lighting/animation where appropriate. [Screenshot API](https://lua-api.factorio.com/2.1.20/classes/LuaGameScript.html#take_screenshot).

Replace arbitrary post-marker sleeps with an explicit capture-completion protocol: use `game.set_wait_for_screenshots_to_finish()`, require the declared frame/scene set, then decode images fully and verify metadata before shutdown. `force_render` helps schedule requested frames but has documented multiplayer catch-up limits. A PNG signature/dimension check alone does not prove a valid complete capture.

Check native GUI hierarchy, element states, visibility, interaction outcomes and geometry separately from pixel evidence. In an explicitly instrumented single-player lane, `LuaGuiElement.actual_size` exposes post-layout dimensions; it is unavailable as ordinary multiplayer-safe game state. Use it to investigate clipping/layout, not to add instrumentation to release packages.

Use region-specific image comparisons for stable scenes with recorded engine/renderer/locale/scale and justified tolerances. Mask only known nondeterminism, never the changed control. Check meaningful anchors/colors/geometry and review visual differences; do not pass solely because an image is nonblank or globally similar. Include representative long translations, display scales/resolutions, hover/pressed/disabled states, and world-overlay phases. Fonts, tooltips, focus, hit testing and usability may still need narrow actual-input/human checks.

All presentation frames remain **Extreme**, with antialiasing and effective configuration recorded. Generate GIF/video frames from known engine ticks, flush them, then use a pinned encoder and validate ordering, frame count, timing, dimensions and the resulting asset. Never silently reuse low-quality test captures for a thumbnail or gallery. A pixel baseline is reviewed evidence, not something to auto-update when a test fails.

### Multiplayer, determinism, replay and compatibility

Two forces or two LuaPlayer objects in one process do not establish multiplayer safety. For relevant runtime/state changes, add an owned headless server plus real clients: late join after state exists, disconnect/rejoin, save/restart, force changes and concurrent actions. Assert the intended behavior and collect client/server logs and desync reports. Match engine/mod versions exactly. A headless server by itself does not supply a connected graphical player or prove client behavior.

FactorioTest 3.1.0 explicitly rejects multiplayer saves. The peer lane therefore needs separate scenario/client orchestration; enabling companions in its normal single-player suite does not create multiplayer coverage.

Use private networking, isolated profiles and authorized client prerequisites. Multiplayer administration/RCON is confined to these test instances. Do not change the user's multiplayer authentication/security settings or connect to live servers. When a desync occurs, preserve enough time for its report to finish downloading before stopping the owned client. [Desync report requirements](https://forums.factorio.com/viewtopic.php?t=53851).

The installed engine advertises `--benchmark-consistency` (checks before/after the benchmark), `--run-replay`, and graphical single-player `--heavy`. Treat these as targeted diagnostic tools, not proof of every determinism property. Recorded replay fixtures can exercise real input sequences, but compatibility, mod changes, replay-disabling script actions and termination need explicit checks and deadlines.

Instrument Mode can provide profiling/debug hooks and GUI layout measurements; it disables multiplayer because it is not desync-safe. Keep instrumented diagnostic results separate from uninstrumented package and multiplayer proof. Coverage may locate unexercised branches, but a line-coverage percentage does not establish meaningful assertions. [Instrument Mode](https://lua-api.factorio.com/2.1.21/auxiliary/instrument.html).

Choose a risk-based compatibility matrix: declared minimum engine and selected current supported build, base/Space Age where promised, known interacting mods, relevant startup settings, languages/scales, and selected native platforms. Do not assume every pair among 100 mods needs a bespoke test, or that pairwise coverage guarantees all interactions. Keep dependency/load-order and high-risk coexistence cases explicit. Unsupported/unavailable cells are visible, never silently counted as passes.

### Non-GUI debugging and profiling

Factorio exposes a native Debug Adapter Protocol endpoint with `--dap`, using stdin/stdout. A supported DAP client can launch the same isolated fixture, inspect breakpoints/stack state and request `startProfile`/`stopProfile`; `profileComplete` reports the saved trace path. This offers programmatic investigation without driving VS Code or a game console. The installed FMTK uses the native adapter. See the versioned [LuaDebugAdapter contract](https://lua-api.factorio.com/2.1.20/classes/LuaDebugAdapter.html).

Implement this as an explicit diagnostic mode of the same run service, with scoped ownership, typed messages, bounded pauses and trace artifacts. Do not blindly append `--dap` to FactorioTest's current launcher: both consume process stdout for their own protocols, so transport integration must be designed and tested. DAP evaluation can mutate state; keep it in the owned diagnostic fixture and distinguish passive inspection from evaluation. Debug/profiler runs do not replace uninstrumented verification, and were not exercised in this research.

## 6. Development tuners and parameter studios

## 7. Make the verifier prove that it detects failures

Test the shared harness once, not by copying its self-tests into every mod. Its own correctness is a prerequisite for trusting 100 green rows.

Required fault cases include malformed owned configuration, unknown targets, unsupported engine/runtime pairs, missing/corrupt archives, undeclared enabled mods, intentional data and runtime Lua errors, assertion failures, exit zero without a final result, a completion marker without all cases, wrong-run/foreign/stale results, truncated JSON or PNGs, duplicated events, stdout/stderr floods, quiet hangs, noisy hangs, cancellation, owned-process shutdown failure and container OOM reporting. Most orchestration faults can use a small disposable subprocess fixture; use real Factorio fixtures for engine-specific behavior. Do not induce unsafe native crashes on the user's workstation merely to test a classifier.

Add negative controls for the assertions themselves: temporarily alter an owned throwaway package/fixture in a plausible consumer-visible way, such as removing the retirement migration, reversing a detector predicate or omitting a required locale/resource, and require the relevant check to fail for the intended reason. Never mutate the user's working tree for mutation testing. Prioritize uncovered risks over a fleet-wide mutation-score target.

For bugs, retain deterministic failing-before/passing-after evidence where practical. Reduce a failing generated sequence to a small regression fixture. A baseline and candidate sharing a failure is an inherited issue, not automatically a new regression; preserve that distinction without calling the required check green.

## 8. Stack-wide performance and UPS verification

Performance verification is a required capability wherever a mod or tooling change can materially affect it. It covers **the player's simulation and interaction cost as well as development feedback speed**. Use the measure-before/after workflow below; do not infer a performance pass from functional tests, a fast startup, small source size, or a stable displayed UPS counter.

### Metrics and acceptance semantics

At normal 60-update-per-second simulation speed, the whole world has approximately **16.667 ms per update**. This is not a per-mod allowance. Record total engine update time in ms/update, attributable script/callback costs where available, and action-to-result latency in both ticks and wall time. A capped 60 UPS display hides consumed headroom; script time alone omits engine work induced by a mod. Keep simulation UPS, rendered frame time/FPS, CPU utilization and command wall time separate. See [Factorio's performance diagnosis and hidden mod costs](https://wiki.factorio.com/Tutorial:Diagnosing_performance_issues); prefer the selected engine's actual output/API over historical assumptions about renderer scheduling.

For a defined unthrottled simulation window, `1000 / mean_update_ms` is an equivalent update throughput, not a promise of interactive UPS or rendering performance. Report the underlying ms/update first. An extra millisecond does not have a fixed additive “UPS price.” Do not compare means of inverted timings, nested timer sums, total multi-core CPU time, or benchmark startup time as if they were the same metric.

Each performance-capable project/scenario declares its metric, units, workload scale, measured interval, hardware/backend class, baseline identity and applicable cost/latency/memory budget in validated development configuration. Calibrate numerical budgets from representative clean-baseline runs and the intended use, rather than inventing one universal microsecond threshold or dividing the tick budget equally among 100 mods. Include steady-state cost, burst cost and completion latency; optimizing any one must not quietly worsen another beyond its declared contract.

Required measurements can be passed, regressed, inconclusive, or blocked—not absent-but-green. A repeatable new regression or an existing hard resource/latency-contract violation needs resolution or an explicitly recorded user decision. Shared inherited baseline failures remain visible and do not automatically reject an incremental improvement; noisy data does not prove either improvement or harm. Do not automatically bless a slower baseline, loosen a threshold, remove a case or rerun until a lucky sample passes. Performance comparisons never override correctness, determinism, isolation or ownership requirements.

### Coverage across the available stack

| Layer | Required observations and representative pressure | Tools and proof boundary |
| --- | --- | --- |
| Lua and engine simulation | Total ms/update; script/event cost; periodic spikes; garbage-collection contribution; engine work induced by entities, paths, networks and other changed state | Real fixed-save `--benchmark` runs, supported `--benchmark-verbose` categories, bounded LuaProfiler/DAP investigation. Keep end-to-end uninstrumented engine evidence; low script time does not prove low total cost. |
| Lifecycle and persistence | Install/configuration-change surveying, migration, save/load wall time and save size; large maps, surfaces and retained state | Fresh-process fixtures and actual save completion. Record setup/first-use costs separately from warmed steady state, without excluding them from the relevant user-visible operation. |
| Native GUI and renderer | Interaction-to-visible-result latency, frame-time distribution, CPU render preparation, render-object/GUI churn and retained resources across repeated use | Programmatic scenes, supported graphics benchmark/performance output and narrow native interaction checks. Headless timings cannot establish pixel/render cost; capture/encoding time is not normal frame time. |
| Development tuners | Candidate-to-applied/visible latency, idle CPU, overlay count, GUI rebuild cost, session memory and cleanup; parameter sweeps and repeated reset/open/close | Compare product alone, studio idle and studio actively changing values under matched conditions. Measure the proxy/observer separately; never attribute its cost or its faster alternative rendering to the shipped mod. |
| Bun, Effect and Effect Schema | Real command startup/completion; discovery, decode/encode, filesystem staging, hashing, scheduling and result parsing; CPU/heap and cancellation latency | Monotonic end-to-end timers and phase spans at the shared service boundary; opt-in Bun CPU/heap profiles. Preserve mandatory boundary validation; avoid repeated parsing/decoding/copying of already validated internal values only when measured. |
| Lua/Python helpers and packaging | Type/model/checker phases, generated API preparation, archive creation/verification and compression; wall time, peak memory and deterministic output | Existing pinned tools through Mise/`uv run`; interpreter-compatible profiling and allocation diagnostics. A helper microbenchmark does not establish faster complete verification or release preparation. |
| Logs and process supervision | Producer-to-reader observability, collector CPU/memory/I/O, backlog, shutdown/drain time; zero, multiple, slow and disconnected readers | Run-correlated host timings and bounded fault/load fixtures. State clock boundaries: host receive-to-persist/read latency is not engine emission latency without valid correlation. Preserve full required diagnostics and read-only subscriber independence. |
| Docker and host resources | Startup/staging cost, CPU limits/throttling, memory pressure/OOM, block I/O and contention; native architecture versus explicit emulation | Scoped container stats/API plus owned process observations, image/platform/limit receipts and end-to-end timing. | Fleet scheduling and artifact delivery | Selected-mod and full-fleet wall time, queue delay, throughput, peak concurrent resources, artifact footprint and cache effectiveness | The real canonical commands with representative project sets. Separate offline execution from downloads/network provisioning. Never benchmark by publishing, dropping validation, or reporting cached work as fresh execution. |

Use the facilities already available before adding dependencies. The pinned Bun CLI advertises `--cpu-prof`, `--cpu-prof-md`, `--heap-prof` and `--heap-prof-md`; its [benchmarking documentation](https://bun.com/docs/project/benchmarking) also describes monotonic clocks and heap diagnostics. Heap snapshots, retained-object counts and process RSS answer different questions. Do not assume a heap-profile interval flag enables allocation sampling; the documented Bun heap profile is a snapshot on exit. A single snapshot or elevated RSS is not proof of a leak.

Use Effect's version-matched span/metric facilities at the canonical runner/services, with run correlation and explicit units; [current tracing documentation](https://effect.website/docs/v4/observability/tracing) illustrates parent/child spans, not a requirement to deploy an observability backend. Report inclusive versus exclusive durations and concurrent critical paths rather than summing overlapping spans. Keep schema/protocol versions pinned together with the chosen Effect stack.

For Python helpers, use the pinned interpreter's supported profiler through `uv run` (for example `cProfile`) and [tracemalloc](https://docs.python.org/3.13/library/tracemalloc.html) when allocation attribution is needed. Detailed tracing changes timing and must remain separate from primary uninstrumented measurements. [Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/) can stream selected-container resource use; record whether memory is the CLI's cache-adjusted value or API accounting. Do not scrape GUI counters as the canonical unattended measurement path when engine/process output supplies the metric.

### Representative simulation and interaction workloads

Start from the current product contract, not an obsolete parameter snapshot. The 1.1.7 [detector](location_location_location/undergrounds.lua) has a persistent fair queue capped at 64 scheduled mouth entries per tick and next-tick dirty-neighborhood priority. Normal validation completes within 60 ticks up to 3,840 mouths; overload takes longer without dropping coverage. Native alert renewal remains a separate 60-tick batch offset from six-tick pulse rendering, and silent scripted changes can require validation plus renewal. Installation/configuration surveys, event bursts, pulse and native-alert batches are outside the background cap. [Per-player preferences](location_location_location/underground_preferences.lua), pair-specific selected-belt suppression and audience changes also require their own workload coverage.

| Scenario family | Required workload and invariants |
| --- | --- |
| Installed but idle | Empty map and large unrelated factory, no pending changes/warnings, planner closed. Establish incremental idle cost and ensure ordinary idle work is not proportional to every unrelated entity. Zero relevant work is not a claim of zero process CPU. |
| Active warnings and spans | Zero plus at least three declared nonzero scales; vary pair distance/tier, surfaces, forces, players, alert settings and pulsing/steady/off audiences. Record actual qualifying entities, visible objects and effective settings. Compare the same mode between baseline and candidate. |
| Event bursts and recovery | Mass build/robot/clone/rotate/mine/destroy and invalidation, followed by quiescence. Measure worst-window update cost, pending-work growth, detection and cleanup latency, completed work and return toward the idle resource baseline. |
| Audience and selection churn | Repeated belt selection changes, join/leave/force changes and mixed player modes. Preserve per-player visibility, selected-belt span suppression and unrelated alerts; an invisible overlay is not automatically free. |
| Existing-factory installation and upgrade | Survey a recorded large map, reconcile state, save and reload. Bound first-use stalls and memory separately from ordinary ticks; no performance gain by silently omitting existing entities. |
| Planner/source lookup and GUI | Representative recipe/plan/source counts, chart/force eligibility, large picker searches, multiple drafts and repeated open/edit/apply/discard. Measure actual completed selection/render and retain deterministic results and private-draft semantics. |
| Long session and cleanup | Fixed bounded duration/action count, repeated create/remove/open/close and save/reload cycles. Track live entities/render objects/GUI/storage and memory trends at equivalent checkpoints; distinguish allocator retention from reachable leaks. |
| Combined mod load | Named representative bundles as the fleet grows, with simultaneously active periodic callbacks and burst actions. Measure total engine cost and spikes; independent per-mod averages cannot establish a combined fleet budget or rule out synchronized stalls. |

Run enough simulation to observe full configured pulse/update periods and intended burst/recovery windows, including periodic alignment, rather than sampling only cheap ticks. Record tick phase and distinguish warm-up, setup, steady state and bursts. The user-approved bounded queue explicitly permits longer overload cycles, not missing work; preserve its normal/overload latency acceptance and report both. Do not stretch those bounds, hide arrows, cap warning coverage or reduce observers merely to obtain a faster result. Any further semantic change needs its own explicit correctness/latency contract.

Where stable operation counters make the contract clearer, assert bounded relevant work and resource lifetime alongside timing: neighborhoods queried, pending items processed, warning/render objects retained and objects removed after cleanup. Put diagnostic counting at the actual owned operation boundary, keep it opt-in where costly, and do not duplicate production logic in the oracle. Trend tests across scales expose possible nonlinear growth; a few timing samples do not mathematically prove complexity.

### Baseline, candidate and measurement protocol

1. Define the user-visible outcome and its completion boundary first. Select a representative fixed save/scenario, seed/action trace and explicit workload counts; preserve assertions and pre/postconditions. Seal source/package, fixture, dependency, toolchain and configuration identities before editing.
2. Use comparable controls: baseline artifact versus candidate on copied instances of the same fixture; optionally a no-target-mod control only when the world/workload remains comparable. A disabled mod or changed recipe/world simulation is not automatically a valid estimate of pure Lua overhead. Treat differences as whole-scenario effects where appropriate.
3. Record engine/build, OS/architecture, CPU class, renderer where relevant, Docker image/limits, cache state, power/thermal/concurrent-load conditions and instrumentation mode. Never benchmark a mutable active checkout or someone else's running tuner. A fresh process is not necessarily an OS-cold cache; do not drop host caches or stop unrelated work to manufacture laboratory conditions.
4. Measure real end-to-end completion with a monotonic clock plus coarse meaningful phases. Use the engine's own update-time units and normalize them explicitly; verbose tick columns may be nanoseconds while summary values are milliseconds. Do not divide startup-inclusive wall time by ticks and call it simulation cost.
5. Warm up deliberately where the scenario requires it, then repeat independent runs. Alternate or randomize baseline/candidate order to reduce drift. Report run count, ticks/actions per run, useful central values and spread, absolute and relative deltas. Individual ticks are correlated, not thousands of independent replications. Tail percentiles need sufficient samples and a declared window; one maximum is not a stable worst-case bound.
6. Use profiles to localize a measured problem, then make one coherent source-level change controlling the requested outcome. Prefer eliminating unnecessary queries, work, allocations/copies or resource churn. Do not replace deterministic operation budgets with wall-clock scheduling inside gameplay, change required behavior, or optimize a large aggregate duration that is off the user-visible critical path.
7. Re-run equivalent baseline/candidate scenarios, correctness checks and relevant native/persistence/multiplayer boundaries. Separate inherited failures, new regressions, benefits and noise. If evidence is inconclusive, report **no demonstrated improvement** and refine a bounded investigation rather than retaining speculative optimization as success.
8. Assess instrumentation overhead under equivalent instrumented/uninstrumented conditions when it could influence the result. After removing temporary probes, smoke the final delivered path and make the final comparison describe that implementation. Record whether retained instrumentation is enabled, opt-in or removed, and how to reproduce the scenario.

Keep source identity separate from an opaque benchmark label. Performance fixtures and capture profiles are part of the input closure; changing them invalidates comparisons and requires explicit baseline re-establishment. A replay/model counterfactual is labeled model-based evidence, not an observed rerun of the real application.

For this extraction, define an explicit comparison scope: the old LLL package containing the detector versus the new LLL-plus-detector package set on an equivalent world/action trace. Record the intentional ownership/mod-set change and assert equivalent planner/detector outcomes; do not silently treat differently scoped receipts as interchangeable. Measure the new detector alone as a separate result: there is no historical standalone-detector baseline to invent. Packaging/namespace changes may require an explicit fixture migration, whose correctness is proved separately before measured windows are compared.

### Performance tooling, live visibility and receipts

Extend the same Effect CLI/run service with a named performance operation, proposed as `mise run perf -- <mod-id> <scenario>`, plus an explicit comparison of two run IDs. Scenarios live beside the owning mod; engine/native/Docker execution, schemas and reporting stay shared. Do not introduce a second process supervisor, separate fleet registry, per-mod timing scripts, or a mandatory telemetry server.

One schema-backed performance receipt carries run/source/package/fixture IDs, backend and instrumentation mode, metric definitions/units, workload and warm-up/measured windows, repeated-run samples/summaries, budget/baseline identity, correctness outcomes, overhead assessment and artifact paths. Decode and cross-check before comparing; reject mismatched workload/units or present an explicit non-comparable result, never coerce missing samples to zero. Reports distinguish engine timings, end-to-end timings, reused evidence and diagnostic-only traces.

Expose bounded live phase/resource summaries through the existing `runs` observation interface, not a high-frequency dump from every Lua tick. Measure collector, persistence and reader overhead with no reader, normal readers and a slow reader. Preserve the required raw logs; rate-limit optional metric sampling at collection rather than dropping diagnostics after expensive formatting. Heavy per-tick profiling is an explicit finite diagnostic mode and must not silently become an always-on shipped-mod cost.

The before/after report uses one comparison table with scenario/source identities, baseline/candidate sample counts, central values/spread and deltas, followed by correctness checks, instrumentation disposition and uncertainty. Store enough bounded samples to reproduce the summary. Scope retention and keep traces/heap snapshots local by default; they can contain more private content than timing summaries.

### Instrumentation disposition and performance safeguards

- **Keep enabled:** cheap shared-boundary run/phase timestamps, exit facts, input counts and already-required diagnostic events with durable operational value. Validate their overhead and avoid per-entity/per-tick allocation merely to populate a dashboard.
- **Keep opt-in:** detailed Lua/DAP/CPU profiles, per-tick timings, heap/allocation snapshots, rich operation counters and high-detail render traces. Use one common diagnostics mode with supported detail selection, not a feature flag per timer. Gate collection itself so disabled paths avoid profiler creation, clock reads, payload construction, formatting and output where practical.
- **Remove:** one-off probes and throwaway runners after their measurements are captured. Preserve repeatable owned scenarios; test retained enabled/disabled paths for equivalent semantics and smoke the cleaned-up final path.

Verify the measurement system too: a controlled slower/allocating or delayed-result fixture must be detected, while a workload change, insufficient sample set, incompatible unit or missing metric must not produce a spurious speedup. Keep timing-sensitive checks on calibrated workers or classify environmental noise explicitly; deterministic correctness/work-count contracts remain ordinary tests. Hardware changes create a new baseline class, not an automatic historical comparison.

### Fast feedback at 100-mod scale

Use a common check inventory to expose what each command actually covers. Fast authoring checks select one mod/scenario/seed; full selected-mod verification covers declared capabilities; release preparation adds exact-package, upgrade and native evidence; scheduled/explicit broader runs cover the risk matrix and soaks. `verify --all` still reports the actual declared scope, and a filtered developer run does not satisfy a fuller release requirement.

Measure provisioning, process startup, prototype loading, scenario setup, assertion ticks, screenshot encoding and teardown separately from total wall time. Record cold and warm runs, cache state, engine/OS/architecture, Docker limits and concurrent load. Compare representative small and larger mods; do not choose fleet settings from one empty-map run.

Iterate test settings until measurements identify the fastest reliable configuration for each workload. Candidates include native versus Docker headless execution, cache strategy, worker concurrency, dependency staging, simulation tick pacing and separate graphical test settings. Preserve the same assertions, effective mod set and meaningful rendering coverage. Require repeated runs and report spread/sample count; do not derive percentiles or a speed ranking from the one-shot probes below.

Use `--benchmark-verbose` and `helpers.create_profiler()` for targeted runtime cost investigation, not wall-clock values inside deterministic gameplay decisions. LuaProfiler deliberately does not expose raw elapsed values to Lua; use its diagnostic output or external timings rather than inventing numeric profiler assertions. Benchmark repeats reload a map within a process and are not repeated cold startups. Track idle cost, steady-state workload, worst burst, large factories, entity churn, warning counts and cleanup after repeated open/close/build/remove cycles. Bound test workloads and collect memory/resource observations; a single process RSS value does not establish a leak.

Start with a small measured concurrency limit and a separate graphics queue. Avoid CPU/memory oversubscription and shared writable profiles. Add affected-run caching only with the input-closure rules in the migration plan, and identify reused evidence as reused. Batch compatible setup only after comparing against standalone checks; shared state must not hide dependencies or create order-dependent successes. Keep a minimal deterministic reproduction bundle when a broad run fails, not an instruction to rerun the whole fleet until it passes.

- [ ] **V-A11 — Instrumentation disposition:** retain cheap useful metrics enabled and detailed diagnostics opt-in through the shared mechanism; verify equivalent disabled behavior and no disabled collection cost where practical. Remove one-off probes, then smoke the final path.

### V-B: Extraction, native and exact-release proof

- [ ] **V-B1 — Preserve behavioral coverage:** migrate the detector's orientation/tier/lifecycle/audience/ownership and bounded-queue regressions, including churn, partial progress, overload and silent-change latency; keep planner invariants independently covered.

- [ ] **V-B11 — Reproduction:** fresh checkout provisions explicit dependencies and exercises required selected/all commands without sibling repos or player profile; missing native/engine prerequisites block the required proof.

### V-R: Before public detector release

- [ ] **V-R1 — Real two-client multiplayer:** run the extracted detector on an owned private server with two actual clients, exercising mixed preferences/selection, join/leave, force/surface changes, warning ownership and deterministic state/save behavior. Capture any desync diagnostics. FactorioTest single-player, synthetic players, benchmark consistency and `game.reload_mods()` are not substitutes. - [ ] **V-R2 — Release readiness readback:** confirm required evidence still matches the frozen release and actual supported engine/dependency matrix; retain explicit limits and obtain separate authorization for publication.

### V-T: Tool adoption and later capability expansion

- [ ] **V-T1 — Strict TypeScript/Effect toolchain:** resolve the timed-out compiler spike, pin a compatible compiler/Effect/Effect CLI/Bun set and prove strict types plus valid/invalid CLI behavior. Do not assume Bun transpilation typechecks.
- [ ] **V-T2 — FactorioTest upgrade decision:** keep the working pinned CLI/framework until candidate 3.8.0 and its patch pass real callers, timeout behavior and third-party mod-lock/primary selection. Record acceptance or rejection; upgrading is not inherently required.

- [ ] **V-T4 — Native blueprint fixtures:** implement the selected narrow Bun interchange codec/schema and use native import/build APIs for direction/pairing truth. - [ ] **V-T5 — Bounded private Bun RCON:** implement scoped auth/connect/command deadlines, validated framing/IDs/UTF-8, buffer/response bounds, serialized in-flight commands, structured schemas, disconnect/cancel cleanup and explicit unknown mutation outcome. - [ ] **V-T6 — Save completion protocol:** correlate command/request/run with engine completion, verify the actual completed ZIP and fresh-process reload of meaningful detector state. The existing marker-67890 research save is only feasibility evidence; stdin is an explicitly chosen mode, not an automatic RCON fallback.
- [ ] **V-T7 — Capture-library decision:** exercise a pinned decoder/diff/encoder combination on actual native frames and negative/corrupt examples; select among researched Bun.Image/Sharp/pixelmatch/ffmpeg/ImageMagick based on need, license and compatibility. - [ ] **V-T8 — Generated and mutation checks:** use deterministic Effect-generated/native action fixtures and replayable seeds for relevant invariants; target plausible consumer-visible faults. Add mutation tooling only where a narrow manual negative control is insufficient; preserve proof limits.
- [ ] **V-T9 — Debug/profiler integration:** exercise FMTK DAP ownership and real profiling output/import before claiming unattended debug or Perfetto/Speedscope support. Adopt Hyperfine/Mitata or log viewers only for concrete uncovered needs, not as parallel orchestration.
- [ ] **V-T10 — Fastest reliable settings:** compare repeated cold/warm end-to-end runs for each representative lane; iterate settings without reducing coverage, postponing measured work or relaxing Extreme assets. Record sample spread and “no demonstrated improvement” when warranted.
- [ ] **V-T11 — Scale/risk expansion:** add required platform/dependency/pY combinations, longer soaks, replay/desync checks and combined-fleet workloads as scope grows. Make missing required proof visible; don't block the detector on an unrelated universal fuzz/render farm.

## 10. Research evidence and limits

Existing source inspected: [environment/profiles](mise-tasks/factorio-env.mjs), [headless runner](mise-tasks/test.mjs), [native runner](mise-tasks/native-preview.mjs), [package smoke](mise-tasks/package-smoke.mjs), [native scenes](tests/native_preview.lua), and installed FactorioTest CLI 3.6.0 process/schema/result code. The current CLI startup watchdog is locally patched to 120 seconds; its output watchdog is not a complete wall-clock supervisor. Existing headless wrappers accumulate output before writing their console log, and native completion includes a fixed post-marker sleep. These are migration targets, not claims that the new runner already exists.

Source inspection also found that the installed FactorioTest process adapter accepts a result message without rejecting a later nonzero/signalled engine exit. The new integration must preserve the actual engine exit/signal, handle spawn errors, and await stream draining before deciding completion—not trust only the outer CLI exit or a parsed `passed` message. Exercise that adapter with controlled subprocess fault cases and pursue a narrow maintained/upstream fix rather than duplicating its whole parser. This gap was source-observed, not reproduced against a crashing Factorio instance.

Safe probes ran in the fresh ignored directory `.factorio-test/verification-research-tsHh6F/`, never the active `tuner-preview`, normal saves/mods, or existing test profiles. They used a disposable probe mod, not the extracted detector or the full LLL regression suite.

That unexpected enabled mod directly motivates validating the actual set. Native runs inherited neither `SteamAppId` nor `SteamGameId`. Not exercised here: standalone graphical launch/capture, native crash dialogs/dumps, real-client multiplayer/desync, replay, full FactorioTest execution in Docker, migration/save-upgrade acceptance, release preparation/publication, or repeated performance tuning. The architecture above describes the work needed to establish those guarantees, not an already-passing verification platform.

The original stack-wide performance amendment was requirements work, not an optimization result. It inspected the then-current detector/preferences, existing engine benchmark output, profiler documentation and pinned Bun CLI profiling options; that amendment ran no representative baseline/candidate UPS campaign or profiler-overhead comparison. The subsequent 1.1.7 detector-only campaign is reported separately near the top of this document. Neither it nor the earlier empty-fixture startup probes supplies whole-stack migration acceptance. Establish the reproducible baseline from the agreed clean source before implementation changes.

## 12. Isolated compatibility spikes

These follow-up observations used `.factorio-test/tool-spikes-9CllZu/`, pinned Bun 1.4.2, and separately installed candidate packages. They changed no production implementation or root dependency pins. Raw results remain local ignored research evidence; they are not release-package inputs or an implemented toolkit.

- **Effect 4.0.5 + `@effect/platform-bun` 4.0.5, MIT:** actual CLI valid/invalid input, streamed stdout before child exit, final stderr/nonzero exit, and scoped child cleanup were exercised. Effect Arbitrary found an intentionally failing integer, shrank it to 10 and replayed that failure. Receipts: `effect-results.json`, `schema-parity.json`, `effect-replay.json`.

- **BELT 4.3.0:** the macOS ARM64 binary was provisioned and its source/configuration inspected. The isolated 600-tick, three-run attempt reached its 180-second outer deadline without a benchmark result. No speed, UPS or supported-platform conclusion follows. The source-observed buffering/profile-ownership mismatches are separate reasons not to adopt it as our runner.
- **Standalone full-client prerequisite:** an authorized official macOS Space Age 2.1.21 download matched the official SHA-256. Sharp/pixelmatch, fast-check state-machine scheduling, full animation decode and profile-viewer import were not exercised. Their earlier candidate status remains.

These are compatibility checks, not an optimization campaign. Host contention and unequal workloads prevent a credible before/after performance comparison. No UPS improvement, fastest test setting, native-render fidelity or complete verification platform is claimed.

## 13. Bun-only blueprint and RCON research

### Scope and actual checkout usage

**Decision: use native Factorio fixtures and a narrow Bun interchange codec; implement one bounded Factorio-specific RCON service when adding private server control. Do not add Draftsman or factorio-rcon-py for these capabilities.** Bun + Effect owns orchestration and resource scopes, Effect Schema owns consumed boundary contracts, and Effect CLI owns public commands. These are implementation selections, not production changes made by this research.

The current [underground tests](tests/undergrounds.lua) already create native entities at offsets `-1, 0, 4, 5`, cover the four cardinal directions and reversed cases, and assert `underground_belt_neighbour`. Neither proposed Python package is used by tracked implementation. Python is still used by [packaging](mise-tasks/package.py), [tool setup](mise-tasks/setup-lua-tools.py) and [type preparation](mise-tasks/prepare-types.py); avoiding two proposed dependencies does not remove that interpreter or justify rewriting those working helpers.

The comparison ran Bun **1.4.2**, Effect/platform-bun **4.0.5**, and actual Factorio **2.1.21 build 87673, mac-arm64**, directly in headless mode with isolated base-only profiles. It required no Steam approval, GUI automation, normal-save access or user interaction. Versioned 2.1.20 API references were checked against this 2.1.21 runtime; other engine/platform combinations are not implied.

The **48 real-engine cases** were six routes × four directions × normal/reversed layouts. Every case asserted the constructed entity count, both underground-neighbour relationships, expected belt directions and differing input/output roles. The [official format page](https://wiki.factorio.com/Blueprint_string_format) documents direct JSON import since 2.0, but is also marked as needing a 2.0 update. Do not use its entire entity-field table as a current schema. For the tested 2.1 format, cardinal directions are `0, 4, 8, 12`, reversed by `(direction + 8) % 16`; underground `type` is `input`/`output`. Use `underground_belt_neighbour`, not a generic `neighbours` property. Set the intended blueprint version explicitly (tested 2.1.21.0: `562954249764864`); do not compute the packed version with JavaScript's 32-bit bitwise operators.

The minimal implementation needs deterministic IDs/order, positions, names, directions, underground roles and the fields consumed by a particular fixture. Unsupported fields fail explicitly. Host shape validation does not duplicate engine prototype/placement rules: import success, actual built entities and neighbour assertions remain required. Future modded reach, competing endpoints, obstruction, quality, circuits, recipes and ghost/event behavior need their own cases before support is claimed.

### Required implementation scope and save semantics

1. **One shared Effect service, not per-mod adapters.** Own connect/authenticate/use/close in a scope; bind private test servers to loopback or an explicitly isolated container network. Generate ephemeral credentials and redact them from argv diagnostics, engine logs and receipts. RCON is plaintext administrative access, not a public log-reading endpoint. Independent live-log readers must not need its credentials or mutation capability.
2. **A bounded Factorio protocol subset.** Incrementally decode fragmented/coalesced TCP frames; validate lengths before allocation, IDs, packet type, terminators and UTF-8. Bound request bytes, buffered/response bytes, queued work and every phase. Use one in-flight command with explicit monotonically allocated IDs and a finite ID policy. No automatic reconnect, backend fallback, quiet-period completion heuristic or replay of a timed-out mutation. The spike used a 1 MiB frame bound and 64 KiB request bound; those are experimental values, not a measured production policy.
3. **Canonical command/result schemas.** Effect CLI decodes public commands into the shared Effect Schema contract. A Lua-side operation returns a versioned, run/request-correlated success/error envelope, validated on receipt. A transport packet, empty response or `rcon.print` alone is not a successful gameplay operation. Keep Lua runtime errors, authentication errors, protocol errors, timeout/disconnect and unknown mutation outcome distinct. Generate any consumed Lua guards from the supported contract subset rather than maintaining a second validator.
4. **Save completion is a workflow, not a transport method.** Serialize saves per owned engine; create the owned save directory; use a unique run-qualified name; record dispatch/acknowledgement separately. Correlate the matching “Saving game as” event with the subsequent completion event, reject overlapping/unrelated save attribution, require the expected archive, validate ZIP integrity and seal its digest. Persistence/upgrade acceptance additionally reloads it in a fresh process and checks expected state. Do not retry a save/mutation automatically after a lost response.
5. **Complete the production fault matrix before shipping.** Keep the exercised wrong-password, fragmentation, Unicode, empty/large response, timeout, disconnect and reload cases. Add coalesced packets, malformed/oversized lengths, wrong IDs/types, truncation, invalid UTF-8, connection/auth timeout, cancellation during each phase, bounded queue/concurrent callers, stale replies and no-replay assertions. Exercise the selected Linux/Docker path too. These unrun cases are implementation acceptance work, not passing claims about the prototype.

The save spike exposed two genuine harness mistakes: a missing owned `saves/` directory, then attributing a previous save's “Saving finished” line to the next save. After correcting the isolated harness, the RCON save had matching start/completion sequence **53/54**, the subsequent stdin save **55/56**, and both archives passed `unzip -t`. A fresh server loaded the RCON archive and returned the expected persisted marker **67890**. This proves the exercised persistence path; it is not migration, crash-durability, power-loss or multiplayer-client proof.

Two independent readers also consumed the same durable log prefix while the engine was still running. That demonstrates the stream/file mechanism, not the complete future run-discovery/cursor/reconnection API. All owned engines in the final comparison and reload runs exited 0 and were reaped by the supervisor.

### Stack cost, evidence and remaining uncertainty

**Removing the proposed Python dependencies genuinely simplifies these two capabilities, but does not make the repository Python-free.** For fixtures it avoids a second prototype/data-stage model, `lupa`, environment synchronization and a host-language handoff when the real engine is already the oracle. For RCON it keeps cancellation, credentials, streams and typed errors in one Effect scope. The counter-cost is ownership of a small protocol implementation and its fault tests; do not describe that as free or already production-ready. The existing Python packaging/setup helpers remain intentionally unchanged, with their schema-boundary work still applicable.
